# 00 使用方法：从只会 Go 语法开始

## 本章前置

你只需要知道：变量、函数、结构体、接口、切片、map、goroutine 和基本错误处理。即使 goroutine 还不熟，也可以先读。

## 本章目标

读完后，你应该知道学习项目和背项目的区别，并能执行本手册的学习循环。

## 不要一开始背技术名词

错误方式是：

```text
WebSocket、gRPC、Redis、Kafka、Etcd、K8s……
```

把这些名字背完，并不代表知道一条消息怎样从 A 到 B。正确方式永远从问题开始：

```text
用户要做什么？
程序收到什么输入？
哪段代码处理？
数据保存在哪里？
成功怎样返回？
中间失败怎么办？
```

## 一个功能的六步学习法

以“登录”为例，但本章不解释登录实现：

1. 用一句话说用户行为：用户提交账号和密码。
2. 画入口和出口：浏览器发请求，服务器返回成功或失败。
3. 找 Go 入口函数。
4. 找函数使用的结构体和依赖。
5. 找数据读取位置。
6. 列出至少一个失败情况。

以后单聊、群聊、红包和 AI 都使用同一方法。

## 每章的实际动作

按下面顺序做，不要只阅读：

```text
读一遍
→ 合上文档画图
→ 用自己的话讲一遍
→ 打开代码找锚点
→ 回答闭卷题
→ 第二天再讲一次
```

第一次只要求知道“为什么”和“经过哪里”；第二次再看结构体；第三次才研究失败路径和性能。

## 遇到陌生词怎么办

先记录五个问题：

```text
它解决什么问题？
没有它会怎样？
为什么当前项目选择它，而不是更简单的替代方案？
使用它要付出什么代价，它又不能保证什么？
它在项目哪一段出现？
```

这五问分别对应问题、后果、选择理由、边界和代码位置。不要立刻跳到网上看几十页源码；先能用自己的话回答这五问，再继续追实现。当前章节没有解释的词，会在后续第一次需要它时解释。

## 三条红线

1. 不会时说不会，不用技术名词掩盖调用链。
2. 文档与代码冲突时，以当前代码和测试为准。
3. “设计上可以”不等于“真实生产验证过”。

## 本章代码阅读任务

本章只做一次源码定位，不理解业务实现。

| 顺序 | 打开位置 | 这次只看什么 |
| --- | --- | --- |
| 1 | `cmd/gateway/main.go` 的 `func main()` | 找到 Gateway 进程入口，以及 `handler.RegisterHandlers` 这一行 |
| 2 | `cmd/logic/main.go` 的 `func main()` | 确认 Logic 是另一份可独立启动的程序 |
| 3 | `cmd/transfer/main.go` 的 `func main()` | 确认 Transfer 还有第三个进程入口 |

看到这个程度就停：你能用 `rg "func main" cmd` 找到三个入口，并能说出“三个 `main` 运行后是三个进程”。暂时不必看配置覆盖、goroutine、Kafka 消费循环和依赖初始化；后续章节会在第一次需要时拆开。

## 闭卷检查

1. 学习一个功能时要问哪六件事？
2. 为什么不能先背所有中间件名字？
3. “已实现”和“演进方案”有什么区别？
4. 第一次遇到一个技术名词时，应该先回答哪五个问题？

四个问题能自然回答后，再进入第 01 章。

## 闭卷检查参考答案

1. 依次问：用户做什么、程序收到什么、哪段代码处理、数据存在哪里、成功怎样返回、中间失败怎么办。
2. 中间件名称不能说明它解决的业务问题，也不能说明它处在调用链哪一段。先从用户行为和故障出发，才知道是否需要某项技术。
3. “已实现”必须能在当前代码或测试中定位；“演进方案”只是下一版可以怎样设计，不能写成现在已经具备。
4. 问它解决什么问题、不用会怎样、为什么选它而不选更简单的替代、代价和不能保证什么、在项目哪一段出现。
