# 01 从用户角度认识 IM

## 本章前置

只需要完成第 00 章。本章不要求理解网络、数据库或分布式系统。

## 本章目标

你要先知道 LinkGo 对用户提供什么，而不是先看内部组件。

## IM 是什么

IM 是 Instant Messaging，即即时通信。最小需求只有两个角色：发送者 A 和接收者 B。

```text
A 输入“你好”
→ 系统接收并处理
→ B 看见“你好”
```

“即时”表示系统尽量实时推送；不表示任何网络故障下都绝不延迟。“通信”也不仅是发送文本，还包括身份、会话、顺序、历史和状态。

## 一个能用的单聊至少要回答什么

1. 系统怎样知道 A 是谁？
2. 系统怎样知道 B 在哪里？
3. 消息是否已经保存？
4. B 在线时怎样立即收到？
5. B 不在线时以后怎样看到？
6. A 重复发送时会不会出现两条？
7. B 收到以后怎样告诉服务器？
8. 多条消息按什么顺序显示？

后面的技术都是为这些问题服务。

## LinkGo 当前用户功能

主线功能：

- 账号登录。
- 添加好友和处理好友申请。
- 单聊与群聊。
- 最近会话与历史消息。
- 断线后的消息补偿。
- 红包创建、领取和详情查询。
- AI 虚拟好友、总结和知识问答。

项目定位是 `IM + 红包 + AI`。红包用于学习数据库并发一致性；AI 是普通消息系统之上的扩展。学习时必须先掌握 IM 主线。

## 客户端和服务端

客户端是用户直接操作的程序，例如网页、手机 App。当前 LinkGo 客户端是 `public/index.html` 单文件网页。

服务端是运行在服务器上的 Go 程序。它接收请求、校验身份、保存数据并向客户端推送消息。服务端不等于一台物理电脑：以后可以把同一个服务运行多份。

当前用户视角是：

```text
浏览器页面
→ 登录
→ 选择好友或群
→ 建立实时连接
→ 发送/接收消息
→ 查询历史
```

## 为什么先不看 Redis 和 Kafka

因为用户不关心系统内部用了什么。只有当我们遇到“B 在另一台服务器”“群成员太多”这类具体问题时，才有理由引入相应组件。

## 本章代码阅读任务

本章只从用户界面认功能，不追后端。

| 顺序 | 打开位置 | 这次只看什么 |
| --- | --- | --- |
| 1 | `public/index.html` 的 `id="username"`、`id="login-btn"`、`id="send-btn"` 等页面控件 | 找到登录、好友、群组、红包、消息输入框和发送按钮，确认当前客户端是浏览器页面 |
| 2 | 同文件的 `login()`、`connectWebSocket()`、`sendMessage()` | 只看函数名和调用先后，不看编码细节 |

看到这个程度就停：你能指着页面说出“用户先登录，再建实时连接，最后选择用户或群发送消息”，并能指出红包和 AI 是 IM 主线之上的扩展。暂时不必理解 `fetch`、Protobuf、Redis 或 Kafka。

## 动手练习

在纸上画三个方框：`用户 A`、`LinkGo`、`用户 B`。画出发送消息方向，再写出上面八个问题。

## 闭卷检查

1. IM 的最小用户行为是什么？
2. 客户端与服务端有什么区别？
3. LinkGo 的主线与两个扩展功能分别是什么？
4. 为什么现在还不应该讨论 Kafka？

## 动手练习与闭卷检查参考答案

动手图应为 `用户 A -> LinkGo -> 用户 B`。八个问题依次是身份、位置、持久化、在线推送、离线恢复、重复发送、接收确认和消息顺序。现阶段不要求写出组件名。

1. A 输入一条消息，系统处理后让 B 看到。这是最小用户行为。
2. 客户端是用户直接操作的程序，当前是 `public/index.html`；服务端是接收请求、校验身份、保存数据和推送消息的 Go 程序。
3. 主线是账号、好友、单聊、群聊、会话、历史和断线补偿；两个扩展是红包和 AI。
4. 还没有遇到群消息扇出和异步消费的问题。此时先背 Kafka，只会记住名称，无法解释它为什么出现。
