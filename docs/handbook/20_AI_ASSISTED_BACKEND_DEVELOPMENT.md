# 20 AI 辅助后端开发：真实问题、工作差异与面试口径

这一章不再教新中间件，而是复盘这个项目实际开发时怎样出错、怎样定位，以及 AI 生成代码为什么仍需要工程判断。只背 WebSocket、Redis 和 Kafka 名词，无法应付“你真正解决过什么问题”的追问。

## 一次完整开发循环

```text
先写业务不变量和当前边界
→ 让 AI 定位相关文件并提出小范围方案
→ 人工检查调用链、并发与数据所有权
→ 先补失败测试，再修改代码
→ fmt / vet / unit / race / build / docs
→ 查看 staged diff 与敏感信息
→ 推送功能分支
→ 远端 CI
→ 记录失败原因、修复与仍未覆盖范围
```

AI 适合搜索代码、生成测试骨架、列故障窗口和做机械修改；人必须决定业务语义、事务边界、幂等键、状态所有权和证据口径。

## 本项目真实遇到的问题

### 1. 本地 race detector 缺少 C 编译器

`make test-race` 首次失败在 `runtime/cgo`，不是 Go 代码竞争，而是环境找不到 `gcc`。当前机器没有免密 sudo，因此安装用户级 Zig 工具链并提供 gcc 兼容入口，随后 race suite 全部通过。

排查原则：先读第一条编译错误，区分“测试发现 race”和“测试工具根本没启动”。公司项目通常把 gcc、Go 版本和依赖锁进 devcontainer/CI image，减少开发机差异。

### 2. 功能分支推送后没有远端 CI

原 workflow 的 `push.branches` 只包含 `main/master`。代码已经上传，但新功能分支没有 run；这不是 CI 通过，也不是 CI 失败，而是根本没有触发。现改为所有 push 与 PR 都运行，避免合并前没有远端证据。

### 3. 十 Gateway 压测先后暴露五类问题

- WebSocket 压测器没带 `Origin`，握手全部 403。
- Read Deadline 失败后继续读取同一连接，引发 gorilla/websocket panic。
- Etcd 注册 key 带前导 `/`，resolver 归一化后订阅路径不一致。
- 压测账号没有好友关系，被真实业务授权正确拒绝。
- Gateway 只等待 Logic 容器启动，没有等待 ready，造成启动竞争。

这些问题说明“服务启动”“端口能连”“业务请求能成功”是不同层次。完整记录见 `benchmark/bench_report_20260816.md`。

### 4. 红包并发测试先撞到数据库连接上限

200 个 goroutine 并发领取时，客户端连接池最初设为 240，MariaDB 返回 `Too many connections`。这不等于红包超卖；应先把资源配置问题与事务正确性分开。将连接池限制为 100 后，100 份红包恰好 100 人成功、金额守恒。

sqlmock 只能验证 SQL 顺序和分支，真实 MySQL 并发测试才覆盖锁等待、连接池和唯一键竞争；短时本机结果仍不能外推生产容量。

## AI 辅助开发最容易犯的错误

1. AI 根据文件名猜调用链，没有继续追到真实入口和失败出口。
2. 为“可靠性”堆 Kafka/Redis，却没有定义事实源、幂等键和提交位点。
3. 看到 goroutine 就说并发安全，忽略共享状态、队列上限、取消和资源回收。
4. 修改 SQL 与 Go model 不同步，或者只改 `init.sql`，没有增量 migration。
5. 生成大范围重构，混入无关格式化，使 review 无法判断真正行为变化。
6. 把压测器写入成功当作服务端接受，把本机短测写成生产 QPS。
7. 把示例密码、Token、DSN 或日志中的消息正文提交到 Git。

使用 AI 时，每次都要追问：证据在哪里、失败窗口是什么、测试到底覆盖哪一层、这句话能否从代码和运行结果证明。

## 和实际公司后端工作的差异

| 当前项目 | 实际工作通常还需要 |
| --- | --- |
| 单账号单 route、短期 Redis 补偿 | 多端同步、推送游标、跨端已读、长期补偿任务 |
| MySQL/Redis/Kafka 单稳定入口 | HA、容量规划、备份恢复、变更演练和 SLO |
| Logic 写库后直接 Redis/Kafka 投递 | Outbox/CDC、补偿扫描、去重和跨系统对账 |
| 本地 Compose 与 K8s 清单 | 镜像供应链、灰度、回滚、权限、Secret 轮换和真实集群证据 |
| 单元/race/短时 benchmark | 预发压测、长稳测试、故障注入、监控告警和 on-call runbook |
| 一个人同时改协议、SQL、服务 | API/DB review、跨团队排期、兼容策略、migration 与发布审批 |

因此面试时可以讲“我实现并验证了协议和故障边界”，不能讲“经历过亿级消息生产流量”或“完成了生产高可用”。

## 秋招面试说法

推荐回答结构：

> 我先做了可运行的多 Gateway IM 主链，再用测试和压测发现实际问题。比如 10 Gateway 压测初次全 403，最后定位为客户端缺 Origin；Etcd 注册路径还存在规范化不一致；race test 也曾因为本机缺 C 编译器根本没有执行。我把这些区分为环境、协议、授权、服务发现和业务一致性问题，分别补工具链、ready 检查和回归验证。当前项目证明的是单机/Compose 环境下的实现与故障分析能力，生产上仍需要多端模型、Outbox、共享中间件 HA、长稳压测和完整发布治理。

如果追问 AI 的作用：

> AI 帮我搜索文件、生成测试骨架和枚举故障场景，但事务边界、幂等键、状态事实源和指标口径由我结合代码与运行结果确认。AI 产出的结论如果没有测试、日志或源码定位，我不会写进简历。

## 实战作业

1. 从 CI 或本地命令选一个真实失败，写“现象—第一条错误—错误层次—根因—修复—回归—残余风险”。
2. 修改一个小功能，要求 AI 先只给文件范围和失败测试，不直接生成完整实现。
3. 对 staged diff 做一次 review，标出 AI 生成但被你拒绝的方案及原因。
4. 给消息写库到 Redis/Kafka 的窗口设计一个演进方案，但明确标记为未实现。

## 本章代码阅读任务

### 每次只复盘一个开发证据

这一章讨论如何使用 AI 开发，但验收对象仍是你能否解释代码。表格每一行单独问：

> 我正在复盘 LinkGo 的 AI 辅助开发过程，现在只学习表格第 X 行。请根据仓库中的真实代码、测试或 CI 配置，先说明这项工作解决了什么，再逐段解释实现和验证过程。请区分 AI 生成建议、我需要做的工程判断、确定性测试证据和仍未验证的部分。最后给出面试中不夸大的表达、一个真实失败复盘模板和 3 道带答案的自测题。

不要把“使用过 AI”写成技术成果，也不要把未运行的测试写成已验证。

| 顺序 | 打开位置 | 必须完成 |
| --- | --- | --- |
| 1 | `.github/workflows/ci.yml`、`Makefile` | 对齐本地与远端门禁，解释为什么 branch filter 会让 CI 根本不触发 |
| 2 | `benchmark/bench_report_20260816.md`、`benchmark/current_protocol_bench.go` | 找出 Origin、读超时、限流反馈和指标口径问题 |
| 3 | `benchmark/redpacket_concurrency_bench.go`、`internal/logic/redpacket.go` | 区分连接池失败、事务失败、业务已抢完和超卖 |
| 4 | `docs/evidence/CURRENT_VERIFICATION.md` | 把每条证据与它不能证明的内容配对 |

看到这个程度：能讲至少三个亲自遇到的问题，并用命令、文件和修复结果证明。暂不要求：不编造线上事故。验收动作：完成一份新的失败日志并加入自己的学习笔记。

## 闭卷检查

1. CI 没有 run、CI run 失败、CI run 成功但测试没覆盖，三者有什么区别？
2. 为什么 AI 生成的并发代码不能只靠 code review 判断正确？
3. 当前项目与公司生产 IM 最大的三个差距是什么？
4. 面试中怎样既讲出工程深度又不夸大？

## 参考答案

1. 没有 run 是触发配置问题；失败要读第一条真实错误；成功只证明 workflow 实际执行的步骤，未覆盖路径仍未知。
2. 并发问题依赖调度、共享资源和外部组件，需要 race、并发测试、真实数据库/Redis/Kafka 集成和故障注入共同验证。
3. 可答多端同步与长期补偿、跨系统可靠投递/Outbox、共享依赖 HA 与完整发布运维。
4. 使用“当前实现—验证证据—已知边界—生产演进”四段式，每个数字附环境和样本，不把方案说成经历。
