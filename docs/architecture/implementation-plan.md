## 必须先通过的门槛

1. **步骤 0 → 1**：明确当前 `delivery_outbox` 未提交改动如何纳入实现基线。避免在旧代码/旧 Schema 上做一个无法保证通知的任务功能。
2. **步骤 1 → 2**：新表 DDL 能在空库和旧库运行，且不用真实用户库试迁移。
3. **步骤 2/3/4 → 6**：业务状态和授权已经单独可测；通知失败不能改变业务事实。
4. **步骤 6 → 7**：内部发布入口只从已提交事件读取目标；不能允许普通客户端伪造系统消息。
5. **步骤 7 → 8**：页面必须可完成任务闭环，而非只有 API 调试按钮。

## 自动化测试矩阵

| 类别 | 最低用例 |
| --- | --- |
| 状态机 | 草稿发布一次、重复发布、发布后编辑、截止后提交、待审时关闭、关闭后提交 |
| 权限 | owner/admin/member/非成员/removed；跨群 task ID；普通成员读取他人答案与理由 |
| 幂等/并发 | 同一 `request_id` 重放、同 ID 不同 payload、双击提交、两管理员并发审核、旧 `expected_version` |
| 事务 | 任务行写成功但事件/待办插入失败时全部回滚；DB commit 成功但 worker 不可用时 HTTP 仍成功 |
| 通知 | Redis/Kafka 故障、任务待办租约超时、消息已写但待办未标 done、IM 投递重复、成员移除后待办领取 |
| 前端 | 三账号完整旅程、刷新持久化、提醒点击后查最新详情、通知延迟时主动刷新、过期 JWT |

## 最小可独立演示的旅程

按依赖完成步骤 0～7 后，先只演示“**A 发布一项任务 → B 提交 → A 退回 → B 重交 → A 通过并关闭**”。这条旅程跨群权限、MySQL 状态、事件通知、现有群消息链和 Web 页面；用 C 验证越权，再断开通知 worker 验证任务事实与消息提醒分离。此时才进入步骤 8 的独立复核；不能因为某个单测通过就称 IM-P1 完成。

## 会话交接与独立审查

实施会话应以此文档及 `specification.md` 的状态和错误契约为输入，按步骤提交，不顺手进入 IM-P2。独立审查者重新核对源码、迁移、浏览器行为、DB 状态与故障日志，并逐项标记“实际运行通过/仅测试存在/未验证/缺失”。本设计包尚未经过独立复核或批准，实施前应先完成该审查。
